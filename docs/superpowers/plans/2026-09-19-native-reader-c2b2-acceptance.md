# Native Reader C-2b-2 (Measurements, Privacy Observations, Manual Checklist, Acceptance of Sub-project C) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This repo has NO git: the skill is adapted — no worktree, no commits, reviewers get file paths and run reproducing probes, the controller keeps a ledger in the session scratchpad. **Most of this plan cannot be run by agents alone:** every step marked **OWNER** needs the owner at the machine, and the controller runs those steps itself, in conversation with him — subagents cannot talk to the owner.

**Goal:** Put numbers and observations where sub-project C still has assumptions — accuracy and toolbar-band acceptance on the Rust-greyscale path, the privacy behaviours nobody has watched (a Safari private window skipped, a Chrome bookmarks bar, revocation), the manual checklist of spec section 7 — and close spec section 9 "Done means" for the native reader, or hand the owner each shortfall with its numbers.

**Architecture:** Sessions with the owner, each built around an instrument that already exists: `pnpm --dir app reader:eval` (staged windows, run inside the granted dev bundle, results hold numbers only), the app's own `app.log` (fixed codes and count keys, read only with the one permitted `grep`), and process facts (`ps`, `pgrep`). Session 1 is a shake-down, because `reader:eval` has never met a screen and its developer listed 22 things only a screen decides. Code changes happen only in three places — Task 1 (small harness additions), harness repairs found by the shake-down, and the band rule if the bookmarks-bar measurement demands it — and every one of them goes through develop → independent review with reproducing probes, exactly as in C-2b-1.

**Tech Stack:** as C-2b-1 (Rust 1.98.1 offline, TypeScript 7.0.2, vitest 5.0.1, Electron 44.4.1); Google Chrome and Safari as installed; macOS Terminal; no new dependency.

**Spec:** `docs/superpowers/specs/2026-09-18-native-reader-design.md` — section 6 (P4/P5 thresholds), 7 (testing, manual checklist), 9 (Done means), 10.1, 10.2. Input: the table "Status of the carried items after plan C-2b-1" and "New items opened by C-2b-1" at the end of `docs/superpowers/reviews/2026-09-19-native-reader-c2a-first-run.md`. ## Global Constraints

- NO git. Never `cd`. `pnpm --dir app <script>` from the repo root. No downloads or installs without the owner's approval for that execution (this includes installing a browser in Task 9).
- Never run `pnpm` against a copy of `app/` whose `node_modules` is a symlink; call vitest, tsc and `build-native.mjs` directly there. A test never imports a script that does work at top level. The write tools decode backslash escapes into literal characters: generate such text by script and byte-check it.
- **Thresholds are the spec's and are never changed by an agent:** chat ≥ 0.97, tickets ≥ 0.97, terminal ≥ 0.95, Portuguese ≥ 0.95 with accents kept (accents = 1.0), code ≥ 0.90; toolbar: host ≥ 19/20, private label 20/20, false-private 0. They are pinned in `app/src/readerEval/thresholds.ts` by a test. A shortfall goes to the owner with the numbers (minimum and median per case, the confusion pairs the harness printed), and the owner decides: accept with a recorded qualification, change the staging, change the product, or stop.
- PRIVACY. Agents never make the helper capture or recognise a real window, never print a window title or recognised text. Everything that reads a screen happens with the owner present: inside the app, or through `reader:eval`, whose guard reads only a window it staged in this run (exact app, title carrying this run's nonce, `read` naming that window) and whose results hold numbers, booleans, case names and fixed codes only. Never open, print or copy anything under `~/Library/Application Support/Clave Agent Dev/` except `grep -o '"code":"[A-Z_]*"' …/app.log | sort | uniq -c`. **New in this plan, and the only widening:** count keys of two codes may be read with `grep -o '"code":"\(CAPTURE_OFF\|READER_NOTHING_TO_READ\)"[^}]*}' …/app.log` — those lines hold a code, a timestamp and numeric tallies under fixed key names, by construction and by test (`log.ts`'s closed key set); if such a line ever shows anything else, STOP and report.
- The dev bundle is launched only through LaunchServices (`pnpm --dir app start:reader[:scripted]`, `pnpm --dir app reader:eval -- …`), never by running its executable. Before every `dev:bundle` the app is quit and `pgrep -f "Applications/Clave Agent Dev.app/Contents/MacOS"` prints nothing (the script now refuses otherwise, and refuses when `pgrep` gives no answer). OWNER-only: System Settings, granting and revoking, `tccutil`, the keychain, rebooting, deleting things in `~/Applications`.
- During a staged run the owner's own Chrome windows are minimised or closed (the eval uses its own profile and kills only processes carrying its exact `--user-data-dir=`), and nothing private is on screen in Safari during `observe`. Tell the owner before each run how long windows will open and close.
- Record owner statements verbatim in the ledger when made, and later corrections too. Record every measurement with: date, macOS version, display and scale, Chrome and Safari versions, the results file name, and whether another heavy process was running.
- Every code change: developed in a scratch copy with tests proven by reverting the fix, installed by checksum, then an independent review with reproducing probes; `pnpm --dir app test`, `typecheck`, `test:native`, `build:native` (zero warnings), handshake, `smoke` all green afterwards. Baseline at the start of this plan: **1563 passed in 87 files**, native **231**.

Candidate band rules for E3, to be weighed with the numbers, not decided here: **(a)** a second, taller measured band for Chrome when the strip shows more than one toolbar row (needs a reliable row count); **(b)** anchor the band to the recognised address row — the band ends a fixed margin below the line that parses as `host[:port]/…` within the top N points — so extra rows above or below move with it; **(c)** keep the band and have the core refuse to KEEP a Chrome read whose strip shows no address row at all (fail closed: unknown toolbar layout means not read). (c) is the only one that is safe without new measurements and may be wanted in any case.

**Interfaces — Produces:** results gain `helper: {readyMs: number}` (milliseconds from spawning the helper to its `ready`); a new mode `coldstart` that spawns the helper, waits for `ready`, asks `permission`, shuts down and writes only `{mode, helper:{readyMs}, permission}` — it never sends `frontWindow` or `read`; an option `--position <x>,<y>` (points; integers; default unchanged) applied to every Chrome staging so that a run can be placed on another display; `observe` accepts hand-staged **Google Chrome** windows as well as Safari (case names `chrome-normal-…`, `chrome-private-…`, same guard, same D17 rule, `lines:true` so `privateBottomPx` and `bandPx` are recorded).

- [ ] **Step 1: Develop in a scratch copy** (method of C-2b-1: copy `app/` without `node_modules`/`dist`/`target`/`reader-eval/out`, symlink `node_modules`, call the tools directly). Tests first. Must exist: `coldstart` writes no `read`/`frontWindow` line to a fake helper (assert the lines sent); `readyMs` is a number ≥ 0 and nothing else is added to results (the sentinel test still passes); `--position` parses `120,80`, refuses `a,b`, `1`, `-5,3.2`; the position reaches `--window-position=`; an unknown mode is still `BAD_MODE`; `observe` approves a Chrome window only through the same guard (wrong app, wrong nonce, another case's title → no read); `summarise` still never accepts a run that measured nothing, and `coldstart` has its own verdict (`readyMs` recorded, `permission` = `granted`).
